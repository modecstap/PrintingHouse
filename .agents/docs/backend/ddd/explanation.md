# Зачем делить бизнес-логику и инфраструктуру

Бизнес-логика описывает процесс: состояния, переходы и инварианты. Это прямое отображение процесса, как он есть.

Инфраструктуры в этом процессе нет. Она нужна приложению: ORM, SQL, HTTP DTO, обработчики, внедрение зависимостей, брокер, менеджер транзакций, лог, кэш, клиенты внешних API. Замена базы или HTTP не меняет инвариант.

Инвариант клади в агрегат. Он остаётся в агрегате, пока живут и SQL, и обработчик.

Правила: [справочник](reference.md). Шаги: [инструкция](howto.md). Структура берётся из справочника. Код ей противоречит — верен справочник.

## Агрегат — одна транзакция

Агрегат — граница транзакции. Его части сохраняются одним `Save` либо не сохраняются. Свой `Save` у части разрывает границу: в базе одна часть изменится, другая нет.

Снаружи состояние меняет только метод корня. Вызов метода вложенной части обходит проверку, которую корень делает для всех частей вместе.

Агрегат держат маленьким. Чужой агрегат внутрь не вкладывают. В поле лежит его ID. ID называет чужой агрегат и не переносит его состояние.

## Сервис

Агрегат базу не открывает. Иначе инвариант смешивается с SQL.

Сервис — бизнес-код. Он принимает команду, загружает агрегаты и сохраняет их. Один агрегат: загрузить, вызвать метод корня, сохранить. Доменная ошибка обрывает сценарий до записи.

Сценарий на несколько агрегатов в корень не кладут. Корень соседей не загружает. Его собирает сервис и каждый агрегат трогает только методом корня.

## Репозиторий и version

Интерфейс репозитория идёт вместе с агрегатом. Реализация в инфраструктуре собирает объект из базы и разбирает его обратно. Сборка из базы — единственное место, где код снаружи агрегата пишет в его поля.

`version` показывает, та же ли строка в базе, что локальная копия. Без поля два сохранения молча затирают друг друга.
